    ## Draft: Card Network Refund vs. Reversal Rules and Refund Windows (Visa/Mastercard)

    **Core distinction (the heart of the workstream):**

    - **Authorization reversal (void)** cancels an authorization *before* settlement
    — time-limited, no separate credit transaction.

    - **Refund / credit** returns funds *after* settlement and must reference the
    original transaction, generally returning to the **same card** used in the original
    purchase.

    **The compliance point that matters most:** card network rules generally prohibit
    refunding to a different card or account than the original purchase. This is simultaneously
    a network rule and an AML control — directly relevant to the operations concern
    about merchants moving funds between unrelated cards or recipients.

    **Refund windows:** Visa/Mastercard generally allow extended windows (often 120+
    days), but the practical window is set by the acquiring-partner/processor agreements
    and card product — not a single public standard. These must be confirmed per partner
    before launch.

    **Design implications for the tool:**

    1. Default to original-source-only refunds.

    2. Treat reversal and refund as distinct flows with different windows/controls.

    3. Manual overrides for closed accounts should be limited to processing to the
    *original* source — not authorizing a destination change. A destination change
    is a materially higher-risk exception.

    4. Configure windows per partner, not a single hard-coded default.

    **Recommendation (draft):** Launch card refunds with a hard original-source-only
    default; treat any destination change as a high-risk exception (or prohibit it);

## Draft: Card Network Refund vs. Reversal Rules and Refund Windows (Visa/Mastercard)
**Core distinction (the heart of the workstream):**
- **Authorization reversal (void)** cancels an authorization *before* settlement — time-limited, no separate credit transaction.
- **Refund / credit** returns funds *after* settlement and must reference the original transaction, generally returning to the **same card** used in the original purchase.
**The compliance point that matters most:** card network rules generally prohibit refunding to a different card or account than the original purchase. This is simultaneously a network rule and an AML control — directly relevant to the operations concern about merchants moving funds between unrelated cards or recipients.
**Refund windows:** Visa/Mastercard generally allow extended windows (often 120+ days), but the practical window is set by the acquiring-partner/processor agreements and card product — not a single public standard. These must be confirmed per partner before launch.
**Design implications for the tool:**
1. Default to original-source-only refunds.
2. Treat reversal and refund as distinct flows with different windows/controls.
3. Manual overrides for closed accounts should be limited to processing to the *original* source — not authorizing a destination change. A destination change is a materially higher-risk exception.
4. Configure windows per partner, not a single hard-coded default.
**Recommendation (draft):** Launch card refunds with a hard original-source-only default; treat any destination change as a high-risk exception (or prohibit it); confirm per-partner windows and review the controlling agreements/rules before launch.
